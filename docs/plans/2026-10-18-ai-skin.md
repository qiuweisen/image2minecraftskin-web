# AI 皮肤生成计划

> 状态：设计稿（Codex 起草 → 开发助手审阅修订，2026-10-18）。未实现，未做任何付费生成。文末「审阅修订记录」列出相对 Codex 初稿的改动。

## 目标与范围

AI 皮肤是付费 add-on；现有免费的本地算法保持不变，并继续作为默认入口。
免费结果旁增加入口“AI 版本：让它真的像你”，点击后进入真实生成流程，替换当前 fake-door waitlist；已有 waitlist 邮件在功能上线时发送通知。
本计划只覆盖最小可用闭环：一张照片、一次 KIE 生成、浏览器合成 64x64 PNG、任务历史与一次性积分包，不改现有 SEO URL 或免费算法。
实现基于 `ref-coloring` 的 `fix/generation-flow-history` 分支，待该分支合入后原样复用；不自行设计第二套任务/支付系统。

## 新做内容

### 用户流程

1. 用户在免费本地结果下看到 AI CTA，点击触发 `ai_cta_click`；未登录时先走现有登录，已登录但邮箱未验证时提示验证。
2. 用户选择 jpg/png/webp 照片、`classic` 或 `slim`，确认主体提示并勾选第三方 AI consent；客户端先做尺寸和大小校验。
3. 客户端把源图上传到用户专属 R2 key，服务端再次检查 ownership、MIME、大小、短边和 `AI_SKIN_ENABLED`。
4. 服务端检查用户并发/日限额与余额；从余额 charge 1 credit（注册赠送的 1 credit 也在余额里，无特殊分支）。
5. 创建 `skin.kie` task 后立即返回 `pending`，用稳定 task id 创建 Cloudflare Workflow；重复请求只返回同一 `bizKey` 任务。
6. Workflow 将 R2 源图传给 KIE，按 coloringeasy 现有 backoff 轮询；成功后把 KIE 输出图**存入 R2 作为 `resultRef`**（和 coloringeasy 完全一样），任务即为 `succeeded`；KIE 失败/超时/无图 → 现有自动退款。
7. 用户可以离开页面。任务卡和“我的皮肤”展示时，浏览器读取 `resultRef`（AI 角色图），**在本地实时**跑映射得到 64x64 皮肤（几十毫秒，确定性），显示 3D 预览并提供下载 PNG / 下载原图。
8. 不把映射后的 PNG 回传服务器、不新增 `resultRef` 绑定接口（避免信任客户端上传，也避免“任务成功但用户已离开、皮肤没生成”的半完成状态）。
9. 源照片的 7 天清理由现有 R2 cleanup/cron 承担；清理失败只记录告警，不删除生成皮肤。

### 任务状态

**原样复用** coloringeasy `credit_task` 状态（`pending/running/unknown/succeeded/failed/rejected`）与前端轮询退避，不新定义状态机。前端只改文案。

### 服务端边界

- `startSkinTask` 是唯一 charge 入口，先完成输入验证，再用数据库事务/幂等键创建 charge 与 task。
- KIE submit、poll、结果下载均在 Worker；KIE secret、Stripe secret、Email 配置只读 Worker secret/binding。
- 浏览器只上传源图；服务端只接受该用户自己的 R2 key，不接受客户端提交的 `resultRef`。
- task-result 路由继续使用 session 鉴权、`Cache-Control: private, no-store` 与 `nosniff`。
- 失败退款沿用 coloringeasy 现有实现（ledger `bizKey` 唯一约束保证只退一次），不另加字段。
- 全局 cap 在 start 前读取当天计数；达到 cap 返回可重试错误，不建立 task，也不扣 credit。

### UI 最小改动

免费结果卡保持原有布局，只增加一个同层级 CTA 和余额/价格提示；不新增仪表盘或复杂编辑器。

AI 任务卡复用 coloring card 的尺寸、loading、失败退款和下载动作，图片区域显示最终 Minecraft skin 预览；`pending`/`running` 显示生成中，`unknown` 显示检查中并保留刷新。

设置页沿用 creations 的分页和空状态，名称改为“我的皮肤”；按创建时间倒序，单页 24 条，继续使用 cursor，不加载全量历史。

Stripe checkout 只在余额不足或用户主动购买时出现；价格卡显示 15/50 credits 和一次性说明，购买成功后回到原页面并轮询 webhook 写入余额。

### 非目标

- 不改变免费本地 `mapImageToSkin` 的采样、模板或默认 classic 行为。
- 不做多图输入、姿态编辑、手动像素修图、批量生成、订阅或团队共享。
- 不引入新的队列、消息总线、图像服务或前端状态管理库。
- 不将源照片或 AI prompt 写入 analytics，不开放公开结果 URL。
- 不在本期添加新的 SEO 页面、迁移旧 waitlist 数据结构或重做 auth UI。

### Prompt 与结果契约

KIE Nano Banana 2 固定参数：`model=nano-banana-2`、`resolution=1K`、输入图 = 用户照片（字段名以 coloringeasy provider 实际用法为准）、输出比例 1:1（两个全身角色各占半边，每个约 1:2）。人/宠物由用户在上传时选择（默认“人物”），选择“宠物/动物”时追加变体段落；不做自动识别。英文 prompt：

> Turn the subject in this user photo into one blocky Minecraft-style character. Output ONE square-ish image with the character shown in a fixed two-panel layout: front view on the LEFT and back view on the RIGHT. Standing straight, arms relaxed down (no T-pose), orthographic camera, flat lighting, plain white background, full body visible, square-ish cube head, consistent scale and colors between views, no text, no labels, no extra people or objects. Both views the same height, centered in their half, with a clear white gap between them. Use large flat blocks of color with simple pixel-art shading (like a 64x64 Minecraft skin), an 8x8-pixel style face on the front of the head, no gradients, no shadows on the background.

非人类/宠物追加变体：

> For a pet or non-human subject, make a humanoid Minecraft character wearing the animal's fur colors and pattern, with recognizable animal head features (ears, muzzle, horns, or beak) integrated on the cube head; keep the same two-panel front-left/back-right layout and all constraints above.

### 映射与上传

新建一个小 helper `src/lib/skin/ai-sheet.ts`（约 100 行，纯函数，浏览器运行）：
1. 生成图左右对半切；每半去白底，取非白像素的包围盒（bbox）。bbox 太小/为空/两半高度差 >15% → 判为“布局不合格”。
2. 按 Minecraft 身体比例（总高 32 单位：头 8、身体 12、腿 12；身体宽 8、手臂各 4，slim 手臂 3）从 bbox 算出各部位 crops，传给现有 `mapImageToSkin(front, 'java-64', model, { crops, kind: 'full-body' })`。不使用“固定像素坐标”裁剪，因为模型每次出图位置不完全一致。
3. 背面：对右半同样算 crops，用 `getSkinRegions` 找到各部位 back 面，缩放后覆盖进 texture；侧面/顶底保持 `mapImageToSkin` 的取样结果。
4. 输出用现有 `textureToDataUrl` 生成 PNG。
“布局不合格”时任务卡显示“AI 图不规范”，提供“免费重新生成”按钮：服务端在该任务下允许**一次**不扣费重试（task 关联 `retry_of`，写在 `input_json` 里即可，不加列），防止用户因模型偶发失误吃亏；同一任务只能重试一次。


### 输入、账户与收费

- 只接受 `jpg/png/webp`，最大 10MB，短边至少 256px；客户端提示“一张照片、一个主体”，服务端复用 coloringeasy `input-validation.ts` 检查 MIME、大小、尺寸（Worker 内不做多主体识别，多主体靠 prompt + 免费重试兜底）；涉黄等由模型安全策略拒绝，KIE 拒绝即自动退款。
- 登录后获得 1 次免费 AI generation：直接用 coloringeasy 的 `registerGift`（amount=1），不另造“免费资格”表；邮箱注册须先验证邮箱，Google 登录视为已验证。注意：已有老用户没有注册赠送，上线时用现有 admin 发放能力给老用户补 1 credit（可选）。每次 generation 消耗 1 credit，失败自动退款。
- 一次性 Stripe packs：`$2.99/15`、`$6.99/50`，不做订阅；checkout 前显示余额、失败退款规则和未成年人需监护人同意。
- 首次上传 AI 前必须勾选明确 consent：“照片会发送给第三方 AI model”；源照片保留 7 天后删除，生成皮肤保留到用户删除；更新 privacy page 文案。

### 限流、分析与 SEO

- 每用户最多 1 个并发任务、每日 20 个；全局每日上限由 `AI_DAILY_MAX_TASKS` 控制（建议初始 300 次 ≈ $15/天；超限当天拒绝新任务、不扣费），`AI_SKIN_ENABLED` 为总 feature flag；coloringeasy 的 `credit_guard` 表/逻辑一并复用做并发与日限额。
- `analytics-events.ts` 增加并上报：`ai_cta_click`、`ai_generate_start`、`ai_generate_success`、`ai_generate_fail`、`begin_checkout`、`purchase`；payload 不含照片、prompt 或 secret。
- 不新增或修改现有 URL/content；未来可单独增加 SEO 页面，本期不做。

## 成本估算

KIE Nano Banana 2 1K 约 `$0.04/image`，按平均 1.3 次调用（含失败重试和免费重新生成）约 `$0.05/成功皮肤`；保守按 $0.08 估。每个免费注册约 `$0.05`。Stripe 费用按 `$0.30 + 2.9%`：`$2.99` pack 净约 `$2.60`（约 `$0.17/credit`，成本 $0.05–0.08，毛利约 55–70%），`$6.99` pack 净约 `$6.49`（约 `$0.13/credit`，毛利约 40–60%）。用户买了但没用完的 credit 不产生成本。每日全局 cap 以较低者为准，超限直接拒绝新任务并不扣费。

## 上线、回滚与风险

先在 `AI_SKIN_ENABLED=false` 部署迁移和代码，再对内部账号开启；逐步放量并观察失败率、退款率、KIE 成本和 cap。关闭 flag 即刻隐藏入口并拒绝新任务，已运行任务按 Workflow 完成/退款；迁移只增不删，可安全回滚应用版本。

上线检查顺序：先执行 additive migrations，确认 schema/version；再配置 R2、Email、Stripe webhook 和 Worker secrets；然后以 mock provider 在 preview 环境跑 E2E；最后只给内部 verified account 打开 flag。

放量期间每天检查：`ai_generate_start` 到成功的转化、P95 完成时间、KIE fail/timeout 比例、退款是否在 1 分钟内完成、每日任务数与实际费用、Stripe webhook 重放是否保持单次入账。

成功标准是：免费入口仍可离线生成；AI 任务从 start 到 AI 图入库可追踪，皮肤可随时由该图重算；任意失败不损失 credit；用户只能读自己的 R2 结果；关闭 flag 后新请求在 API 层被拒绝；waitlist 邮件不重复发送。

回滚时保留已生成皮肤和 ledger 审计记录，只停止新入口与新 checkout；不要删除 task 或 credit transaction，以便恢复后继续查询和对账。

所有价格、成本和额度均以配置/ledger 为准，UI 文案不能成为扣费依据；服务端必须重新解析 plan/price ID 并校验 Stripe webhook 签名。

主要风险（最多五项）：KIE 输出不遵守双半布局（用固定 prompt、白底检测和失败退款）；第三方上传/延迟波动（重试、backoff、超时与 degrade）；浏览器映射在极端尺寸失败（固定 panel 校验与 mock/unit）；隐私/未成年人误用（consent、7 天删除、结账提示）；成本失控（用户/日限额、全局 cap、flag）。

## 审阅修订记录（相对 Codex 初稿）

1. **映射改到“展示时在浏览器实时算”，不回传 PNG**：初稿要浏览器生成 PNG 再上传绑定任务，用户离开页面就会出现“已扣费、任务成功、但没有皮肤”的半完成状态，还要新做一个信任客户端上传的接口。现在任务成功 = AI 图已存 R2（与 coloringeasy 一致），皮肤随时可由同一张图重算。
2. **裁剪改为“包围盒 + Minecraft 比例”**：初稿用固定像素坐标，模型每次出图位置不同会裁歪。
3. **删除自定义状态机和新字段**：直接用 coloringeasy 已有状态和 ledger 幂等退款；免费 1 次直接用 `registerGift`，不另造“免费资格”表；迁移只有 1 个、不加自定义列（仅 waitlist `notified_at`）。
4. **补充事实**：目标仓库目前没有积分模块，需整目录复制 `src/credits/*`；去掉订阅逻辑。
5. **新增“布局不合格 → 免费重试一次”**：模型偶尔不按双视图出图，这类失败服务端看不出来，给用户一次免费重来，避免差评。
6. **Prompt 加强**：要求同高、白色间隔、大色块像素风、8x8 脸，更利于映射；人/宠物由用户选择，不做自动识别。
7. **补充**：全局日上限建议值、毛利、waitlist 群发需用户确认文案、老用户补 1 credit（可选）、用户需提供清单表格化。
