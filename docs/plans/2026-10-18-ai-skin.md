# AI 皮肤生成计划

## 目标与范围

AI 皮肤是付费 add-on；现有免费的本地算法保持不变，并继续作为默认入口。
免费结果旁增加入口“AI 版本：让它真的像你”，点击后进入真实生成流程，替换当前 fake-door waitlist；已有 waitlist 邮件在功能上线时发送通知。
本计划只覆盖最小可用闭环：一张照片、一次 KIE 生成、浏览器合成 64x64 PNG、任务历史与一次性积分包，不改现有 SEO URL 或免费算法。
实现基于 `ref-coloring` 的 `fix/generation-flow-history` 分支，待该分支合入后原样复用；不自行设计第二套任务/支付系统。

## 新做内容

### 用户流程

1. 用户在免费本地结果下看到 AI CTA，点击触发 `ai_cta_click`；未登录时先走现有登录，已登录但邮箱未验证时提示验证。
2. 用户选择 jpg/png/webp 照片、`classic` 或 `slim`，确认主体提示并勾选第三方 AI consent；客户端先做尺寸和大小校验。
3. 客户端把源图上传到用户专属 R2 key，服务端再次检查 ownership、MIME、大小、短边和 `AI_SKIN_ENABLED`。
4. 服务端检查用户并发/日限额与余额；首次免费资格使用唯一 ledger key 原子领取，否则从余额 charge 1 credit。
5. 创建 `skin.kie` task 后立即返回 `pending`，用稳定 task id 创建 Cloudflare Workflow；重复请求只返回同一 `bizKey` 任务。
6. Workflow 将 R2 源图传给 KIE，按 backoff 轮询；成功时把 KIE 输出 URL 暂存并返回结果元数据，失败进入退款路径。
7. 浏览器轮询 task status；得到 KIE 图后执行双半切分、front 映射和 back face 覆盖，生成 PNG 并上传 user-files R2。
8. 客户端提交最终 PNG 的 `resultRef` 绑定 task；服务端只接受该用户、该 task 的 key，完成后展示下载和“我的皮肤”。
9. 源照片的 7 天清理由现有 R2 cleanup/cron 承担；清理失败只记录告警，不删除生成皮肤。

### 任务状态契约

`pending` 表示已扣费且等待 Workflow；`running` 表示已提交 KIE；`unknown` 表示轮询暂时无法确认；`succeeded` 必须同时有 `resultRef`；`failed` 必须带可展示的失败原因和已完成退款标记；`refund_pending` 只允许短暂存在，恢复任务会重试退款；`rejected` 表示校验/余额/限额拒绝且未扣费。

状态 API 只返回当前用户自己的 task。前端初始 2 秒轮询，随后 5 秒、10 秒、15 秒，最大 30 秒；终态停止轮询。Workflow 内部使用 coloringeasy 的指数 backoff、5 分钟 step timeout 和 15 分钟总窗口，不在浏览器暴露 KIE job id。

### 服务端边界

- `startSkinTask` 是唯一 charge 入口，先完成输入验证，再用数据库事务/幂等键创建 charge 与 task。
- KIE submit、poll、结果下载均在 Worker；KIE secret、Stripe secret、Email 配置只读 Worker secret/binding。
- 浏览器只上传用户拥有的源图和最终 PNG；不得接受任意 `resultRef` 或跨用户 R2 key。
- task-result 路由继续使用 session 鉴权、`Cache-Control: private, no-store` 与 `nosniff`。
- 每次失败都调用一次 `refundCredit(taskId)`；以唯一 `refund_transaction_id` 防止 Workflow 重启重复加回。
- 全局 cap 在 start 前读取当天计数；达到 cap 返回可重试错误，不建立 task，也不消耗免费资格。

### UI 最小改动

免费结果卡保持原有布局，只增加一个同层级 CTA 和余额/价格提示；不新增仪表盘或复杂编辑器。

AI 任务卡复用 coloring card 的尺寸、loading、失败退款和下载动作，图片区域显示最终 Minecraft skin 预览；`pending`/`running` 显示生成中，`unknown` 显示检查中并保留刷新。

设置页沿用 creations 的分页和空状态，名称改为“我的皮肤”；按创建时间倒序，单页 24 条，继续使用 cursor，不加载全量历史。

Stripe checkout 只在余额不足或用户主动购买时出现；价格卡显示 15/50 credits 和一次性说明，购买成功后回到原页面并轮询 webhook 写入余额。

### 非目标

- 不改变免费本地 `mapImageToSkin` 的采样、模板或默认 classic 行为。
- 不做多图输入、姿态编辑、手动像素修图、批量生成、订阅或团队共享。
- 不引入新的队列、消息总线、图像服务或前端状态管理库。
- 不将源照片或 AI prompt 写入 analytics，不开放公开结果 URL。
- 不在本期添加新的 SEO 页面、迁移旧 waitlist 数据结构或重做 auth UI。

### Prompt 与结果契约

KIE Nano Banana 2 固定参数：`model=nano-banana-2`、`resolution=1K`、`image_input=[userPhoto]`、PNG、近似 1:1，调用类型为 image edit。英文 prompt：

> Turn the subject in this user photo into one blocky Minecraft-style character. Output ONE square-ish image with the character shown in a fixed two-panel layout: front view on the LEFT and back view on the RIGHT. Standing straight, arms relaxed down (no T-pose), orthographic camera, flat lighting, plain white background, full body visible, square-ish cube head, consistent scale and colors between views, no text, no labels, no extra people or objects.

非人类/宠物追加变体：

> For a pet or non-human subject, make a humanoid Minecraft character wearing the animal's fur colors and pattern, with recognizable animal head features (ears, muzzle, horns, or beak) integrated on the cube head; keep the same two-panel front-left/back-right layout and all constraints above.

### 映射与上传

新建很小的 `ai-skin-mapping` helper：按固定 1:2 panel layout 切出生成图左半为 front、右半为 back；先验证两半非白背景占比和相同主体高度，再把 front 作为 `mapImageToSkin(source, format, model, { crops: fixedPartCrops })` 的输入。随后用 `getSkinRegions` 找到每个 part 的 `back` face，把右半对应区域覆盖进去；classic/slim 都走同一套 region 尺寸。最终 64x64 PNG 在浏览器用 `textureToDataUrl`/Blob 生成后，通过现有 user-files 上传到 R2，再把 `resultRef` 写入 task。这样复用现有像素算法、减少 Worker 图像依赖；服务端只验证 PNG 尺寸/类型并保存，不在服务端重算。

### 输入、账户与收费

- 只接受 `jpg/png/webp`，最大 10MB，短边至少 256px；客户端提示“一张照片、一个主体”，服务端从 R2 重新检查 MIME、大小、尺寸，并拒绝明显多主体/空图。
- 登录后每账户首次 verified email 获得 1 次免费 AI generation；每次 generation 消耗 1 credit，失败自动退款。
- 一次性 Stripe packs：`$2.99/15`、`$6.99/50`，不做订阅；checkout 前显示余额、失败退款规则和未成年人需监护人同意。
- 首次上传 AI 前必须勾选明确 consent：“照片会发送给第三方 AI model”；源照片保留 7 天后删除，生成皮肤保留到用户删除；更新 privacy page 文案。

### 限流、分析与 SEO

- 每用户最多 1 个并发任务、每日 20 个；全局每日成本上限由 `AI_DAILY_MAX_TASKS` 控制，`AI_SKIN_ENABLED` 为总 feature flag，并沿用 coloringeasy 已有 degrade switch（如分支存在）。
- `analytics-events.ts` 增加并上报：`ai_cta_click`、`ai_generate_start`、`ai_generate_success`、`ai_generate_fail`、`begin_checkout`、`purchase`；payload 不含照片、prompt 或 secret。
- 不新增或修改现有 URL/content；未来可单独增加 SEO 页面，本期不做。

## 数据与迁移（仅 delta）

新增 migration `0006+`：复制 coloringeasy 的 `credit_account`、`credit_transaction`、`credit_task`、必要 payment/refund 字段和索引，增加 `tool_id='skin.kie'`、`input_r2_key`、`result_ref`、`refund_transaction_id`、`provider_job_id`、时间戳。为一次性免费资格增加 user-level unique grant（或等价 ledger idempotency key）；为 waitlist 通知增加 `notified_at`，避免重复发信。已有 `0000-0005` 不回写、不改语义。

## 测试与验收

- Unit：固定双半图切分、front/back face 覆盖、classic/slim region、PNG 输出尺寸；charge/refund 幂等、重复 webhook、并发与每日上限。
- E2E：复制 coloringeasy 的任务卡、状态轮询、失败退款、历史分页和 checkout webhook 测试，全部使用 `mock-provider`；断言不发出 KIE/Stripe 真实请求。
- 输入/隐私：MIME、10MB、256px、未勾 consent、未登录/未验证邮箱、R2 ownership、源文件 7 天清理。
- 真实 sample generation 仅在用户批准约 3 次后进行（预计约 `$0.15`），否则不运行任何付费调用。

## 成本估算

KIE Nano Banana 2 1K 约 `$0.04/image`，按平均 1.3 次尝试约 `$0.05/成功生成`；每个免费注册约 `$0.05`。Stripe 费用按 `$0.30 + 2.9%`：`$2.99` pack 净约 `$2.60`（约 `$0.17/credit`），`$6.99` pack 净约 `$6.49`（约 `$0.13/credit`）。每日全局 cap 以较低者为准，超限直接拒绝新任务并不扣费。

## 用户需提供

Stripe secret key、Stripe webhook secret、两个 Stripe price IDs（或授权创建）、Worker secret `KIE_API_KEY`、R2 bucket name、`image2minecraftskin.com` 的 Cloudflare Email Sending 配置、最终价格确认，以及约 3 次 sample generation 的批准（约 `$0.15`）。

## 上线、回滚与风险

先在 `AI_SKIN_ENABLED=false` 部署迁移和代码，再对内部账号开启；逐步放量并观察失败率、退款率、KIE 成本和 cap。关闭 flag 即刻隐藏入口并拒绝新任务，已运行任务按 Workflow 完成/退款；迁移只增不删，可安全回滚应用版本。

上线检查顺序：先执行 additive migrations，确认 schema/version；再配置 R2、Email、Stripe webhook 和 Worker secrets；然后以 mock provider 在 preview 环境跑 E2E；最后只给内部 verified account 打开 flag。

放量期间每天检查：`ai_generate_start` 到成功的转化、P95 完成时间、KIE fail/timeout 比例、退款是否在 1 分钟内完成、每日任务数与实际费用、Stripe webhook 重放是否保持单次入账。

成功标准是：免费入口仍可离线生成；AI 任务从 start 到最终 PNG 可追踪；任意失败不损失 credit；用户只能读自己的 R2 结果；关闭 flag 后新请求在 API 层被拒绝；waitlist 邮件不重复发送。

回滚时保留已生成皮肤和 ledger 审计记录，只停止新入口与新 checkout；不要删除 task 或 credit transaction，以便恢复后继续查询和对账。

若 KIE 输出持续不合格，degrade switch 将 CTA 改为“稍后再试”，不回退到 fake-door；waitlist 仍可由通知任务处理。

所有价格、成本和额度均以配置/ledger 为准，UI 文案不能成为扣费依据；服务端必须重新解析 plan/price ID 并校验 Stripe webhook 签名。

计划交付物仅为本文件所述设计与验收约束；实现阶段仍须先按 PR 顺序补测试，再接入真实 secrets。

主要风险（最多五项）：KIE 输出不遵守双半布局（用固定 prompt、白底检测和失败退款）；第三方上传/延迟波动（重试、backoff、超时与 degrade）；浏览器映射在极端尺寸失败（固定 panel 校验与 mock/unit）；隐私/未成年人误用（consent、7 天删除、结账提示）；成本失控（用户/日限额、全局 cap、flag）。
